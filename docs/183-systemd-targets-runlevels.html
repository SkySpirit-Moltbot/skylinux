183. Les targets systemd et l'héritage des runlevels

Sur les systèmes Linux modernes, systemd a remplacé le système historique des runlevels SysVinit par un concept plus flexible : les targets. Comprendre les targets est essentiel pour contrôler l'état de votre système, diagnostics de boot, et configuration avancée des services.

Runlevels vs Targets : pourquoi ce changement ?

Les runlevels SysV (0 à 6) étaient simples mais rigides : chaque runlevel déclenchait un ensemble fixe de services, sans possibilité de dépendances complexes. systemd targets offrent :

  • Des dépendances réelles entre services (au lieu de scripts numérotés)
  • La possibilité de combiner plusieurs targets (ex: réseau + syslog)
  • Un parallelisme réel au démarrage (plus rapide)
  • Une migration plus douce via les alias de runlevels

Les targets principaux

TargetÉquivalent SysVDescription
graphical.target5Mode graphique complet avec display manager
multi-user.target3Mode multi-utilisateur texte (sans graphique)
rescue.target1Mode rescue (single user), services de base uniquement
emergency.target-Shell d'urgence, montage minimal du système
shutdown.target0Arrêt du système
reboot.target6Redémarrage
default.target-Target par défaut (généralement graphical ou multi-user)

Visualiser le target actuel

systemctl get-default

Cette commande affiche quel target est défini comme défaut au boot. Exemple de sortie :

graphical.target

Changer le target par défaut

Pour passer au mode texte au prochain démarrage :

sudo systemctl set-default multi-user.target

Pour repasser en mode graphique :

sudo systemctl set-default graphical.target

Le système crée un lien symbolique dans /etc/systemd/system/default.target.

Basculer de target sans redémarrer

Vous pouvez changer de target à chaud (attention : cela peut fermer votre session) :

sudo systemctl isolate multi-user.target

Cette commande arrête tous les services non requis par multi-user.target et démarre ceux qui lui sont nécessaires. Votre session graphique sera fermée.

Lister toutes les targets disponibles

systemctl list-units --type=target --all

Ou de façon plus concise :

systemctl list-unit-files --type=target

Voir quels services sont actifs dans un target

Pour connaître tous les services chargés par un target spécifique :

systemctl list-dependencies graphical.target

Pour voir uniquement les services directs (premier niveau) :

systemctl list-dependencies --plain graphical.target

Targets spéciales utiles

emergency.target — Shell d'urgence

En cas de problème au boot, ajoutez systemd.unit=emergency.target à la ligne de commande du kernel dans GRUB. Vous aurez accès à un shell minimal où le système de fichiers racine est montée en lecture seule.

rescue.target — Mode rescue

Moins minimal que emergency, il monte le système normalement mais n'active que les services essentiels. Idéal pour les récupérations après un problème.

sudo systemctl rescue

halt.target et poweroff.target

Pour arrêter le système de façon propre :

sudo systemctl halt
sudo systemctl poweroff

Créer une target personnalisée

Vous pouvez créer vos propres targets pour des configurations spécifiques. Exemple : un target "serveur" qui n'active que les services nécessaires à un serveur web :

sudo nano /etc/systemd/system/serveur.target
[Unit] Description=Target pour serveur web minimal Requires=multi-user.target After=multi-user.target AllowIsolate=yes

Puis activez vos services spécifiques :

sudo systemctl enable nginx mariadb
sudo systemctl enable --now serveur.target

Comprendre les alias de runlevels

Pour la compatibilité, systemd crée des liens symboliques qui mapent les anciens runlevels vers les targets :

Lien symboliqueTarget réel
/etc/rc.d/rc0.d/K*指向 shutdown.target
/etc/rc.d/rc1.d/K*指向 rescue.target
/etc/rc.d/rc2.d/S*指向 multi-user.target
/etc/rc.d/rc3.d/S*指向 multi-user.target
/etc/rc.d/rc4.d/S*指向 multi-user.target
/etc/rc.d/rc5.d/S*指向 graphical.target
/etc/rc.d/rc6.d/K*指向 reboot.target

La commande telinit reste fonctionnelle pour la rétrocompatibilité :

sudo telinit 3

Cette commande équivalent à :

sudo systemctl isolate multi-user.target

Analyser le processus de boot avec les targets

Pour voir combien de temps prend chaque target au démarrage :

systemd-analyze critical-chain

Pour un affichage plus détaillé par service :

systemd-analyze blame | head -20

Target want et require — Comprendre les dépendances

Quand vous définissez un service, vous utilisez WantedBy= et RequiredBy= dans la section [Install] pour préciser quels targets doivent l'activer :

[Install] WantedBy=multi-user.target WantedBy=graphical.target

WantedBy : le service sera démarré si le target est actif (faible dépendance).

RequiredBy : le target ne peut pas démarrer si ce service échoue (forte dépendance).

Exercice pratique

Étape 1 : Identifier votre configuration actuelle

systemctl get-default whoami # Vérifiez que vous êtes bien root ou avec sudo

Étape 2 : Passer temporairement en mode texte

sudo systemctl isolate multi-user.target

Après cette commande, vous serez en mode texte. Revenez en mode graphique :

sudo systemctl isolate graphical.target

Étape 3 : Explorer les dépendances

systemctl list-dependencies network.target

Résumé des commandes essentielles

CommandeDescription
systemctl get-defaultAffiche le target par défaut
systemctl set-default TARGETDéfinit le target par défaut
systemctl isolate TARGETBascule vers TARGET à chaud
systemctl list-units --type=targetListe les targets actives
systemctl list-dependencies TARGETListe les services d'un target
systemd-analyze critical-chainAffiche la chaîne critique du boot
telinit NChange de runlevel (compatibilité SysV)

Bonnes pratiques

  • Utilisez isolate avec précaution en production — cela change l'état du système
  • Préférez set-default pour les changements permanents de target
  • Sur un serveur headless, définissez multi-user.target comme défaut (plus rapide au boot)
  • Gardez graphical.target par défaut sur les machines de bureau
  • En cas de problème au boot, essayez emergency.target avant de réinstaller
