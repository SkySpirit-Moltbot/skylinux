systemd-cgroups — Limiter et contrôler les ressources système

Introduction

Sous Linux, les cgroups (control groups) sont un mécanisme du noyau qui permet d'allouer, de limiter et de prioriser les ressources système (CPU, mémoire, E/S disque, réseau) entre différents processus ou groupes de processus.

systemd intègre nativement la gestion des cgroups. Chaque service géré par systemd est automatiquement placé dans un slice (tranche), lui-même structuré en scopes et services. Cette hiérarchie permet un contrôle fin des ressources.

Pourquoi utiliser les cgroups ?

  • Isolation : empêcher un service de consummer toutes les ressources
  • Limitation : fixer des plafonds mémoire ou CPU pour des applications
  • Priorisation : donner plus ou moins de bande-passante à certains services
  • Comptabilité : surveiller la consommation de chaque groupe
  • Containers : Docker, Podman et systemd-nspawn utilisent les cgroups en interne

Concepts clés

Slice (tranche)

Un slice est une unité hiérarchique qui contient des processus. Il existe 4 slices par défaut :

SliceDescription
-.sliceSlice racine (contient tous les autres)
system.sliceServices système classiques
user.sliceSession utilisateur
machine.sliceMachines virtuelles et conteneurs

Scope (étendue)

Un scope est un groupe de processus externes gérés dynamiquement (par exemple, les processus d'une session de connexion).

Service (service)

Un service est un groupe de processus lancé et géré par systemd via un fichier unit.

Visualiser les slices et la hiérarchie

Voir la hiérarchie des slices

systemd-cgls

Cette commande affiche l'arborescence complète des cgroups, avec les processus et la consommation de chaque groupe.

Voir les slices actifs

systemd-cgtop

Équivalent de top pour les cgroups. Affiche en temps réel l'utilisation CPU, mémoire et E/S de chaque slice.

Voir le slice d'un processus

cat /proc/PID/cgroup

Affiche les chemins cgroups auxquels appartient le processus PID.

Connaître le slice d'un service

systemctl show nginx.service -p Slice

Limiter la mémoire (Memory)

Via systemctl

systemctl set-property nginx.service MemoryMax=512M

Limite la mémoire maximale du service nginx à 512 Mo. Cette modification est appliquée immédiatement et peut être rendue permanente avec --runtime=false.

Via le fichier unit

sudo nano /etc/systemd/system/monservice.service
[Service] MemoryMax=1G MemoryHigh=800M
DirectiveDescription
MemoryMaxQuantité maximale de mémoire autorisée (hard limit)
MemoryHighSeuil à partir duquel le processus est ralenti (throttling)
MemoryLowQuantité minimale garantie (pas de throttling en dessous)
MemorySwapMaxTaille maximale du swap autorisée

Vérifier les limites mémoire

systemctl show monservice.service | grep -i memory

Limiter le CPU

Via systemctl

systemctl set-property monservice.service CPUWeight=200

Plus la valeur est élevée, plus le service a de priorité CPU par rapport aux autres.

Via le fichier unit

[Service] CPUAccounting=true CPUWeight=500 CPUQuota=50%
DirectiveDescription
CPUAccountingActiver la comptabilisation CPU (requis pour les autres directives)
CPUWeightPriorité relative CPU (1-10000, défaut 100)
CPUQuotaPourcentage maximal du CPU (ex: 50% = 1/2 cœur)
AllowedCPUsListe des CPUs spécifiques autorisés

Limiter à 2 cœurs CPU

AllowedCPUs=0-1

Limiter l'E/S disque

Via systemctl

systemctl set-property monservice.service IOWeight=500

Définit la priorité d'E/S du service (1-10000, plus élevé = plus prioritaire).

Limiter le débit en écriture

systemctl set-property monservice.service IODeviceWeight=/dev/sda 100

Via le fichier unit

[Service] IOAccounting=true IOWeight=400 IODeviceWeight=/dev/sda 200
DirectiveDescription
IOAccountingActiver la comptabilisation E/S
IOWeightPoids global pour l'ordonnancement des E/S
IODeviceWeightPoids pour un périphérique spécifique
IOReadBandwidthMaxDébit maximal en lecture (octets/s)
IOWriteBandwidthMaxDébit maximal en écriture (octets/s)

Limiter à 10 Mo/s en écriture

IOWriteBandwidthMax=/dev/sda 10M

Créer un slice personnalisé

Pourquoi créer un slice ?

Pour isoler un groupe de services avec des limites communes. Par exemple, un slice pour tous les services web avec un plafond CPU partagé.

Créer le fichier unit

sudo nano /etc/systemd/system/mon-slice.slice
[Unit] Description=Mon slice personnalisé pour les services web Before=services.target
[Slice] CPUWeight=200 MemoryMax=2G IOWeight=300

Appliquer et vérifier

sudo systemctl daemon-reload sudo systemctl start mon-slice.slice systemctl status mon-slice.slice

Assigner un service à un slice

sudo nano /etc/systemd/system/monservice.service
[Unit] Description=Mon service dans mon slice [Service] Slice=mon-slice.slice ExecStart=/usr/bin/monservice Restart=always
sudo systemctl daemon-reload sudo systemctl restart monservice.service systemctl show monservice.service -p Slice

Lister les services d'un slice

systemctl list-units --type=service --all --slice=mon-slice.slice

Limiter les tâches (processus)

Nombre maximal de tâches

[Slice] TasksMax=100

Limite le nombre total de tâches (threads + processus) dans le slice. Par défaut, TasksMax=15% représente 15% du maximum système.

Voir la limite par défaut

systemctl show system.slice | grep TasksMax

Limiter le réseau (Network)

Les cgroups réseau permettent de limiter la bande-passante réseau via tc (traffic control). systemd offre une intégration via netclass :

[Slice] NetworkAccount=true NetworkWeight=500
DirectiveDescription
NetworkAccountActiver la comptabilisation réseau
NetworkWeightPoids pour la priorisation du trafic (1-10000)

Pour un contrôle plus fin (limites de débit absolues), utilisez tc directement ou systemd-networkd avec netdev.

Créer un slice pour un utilisateur

Limiter les ressources d'un utilisateur

sudo systemctl set-property --runtime user-1000.slice MemoryMax=4G CPUQuota=200%

Appliqué à l'utilisateur avec UID 1000, cela limite sa session à 4 Go de RAM et 2 cœurs CPU.

Rendre la limite permanente

sudo mkdir -p /etc/systemd/system/user-.slice.d/
sudo nano /etc/systemd/system/user-.slice.d/limits.conf
[Slice] MemoryMax=4G CPUQuota=200%

Surveillance et diagnostics

Vérifier la consommation d'un service

systemctl status monservice.service

Voir les stats d'un service

systemctl show monservice.service

Les propriétés incluent : MemoryCurrent, CPUUsageNSec, TasksCurrent, IOReadBytes, IOWriteBytes.

Surveillance temps réel

systemd-cgtop

Appuyez sur h pour l'aide, p pour trier par chemin, r pour trier par consommation CPU, m pour la mémoire.

Voir les cgroups via /sys/fs/cgroup

ls /sys/fs/cgroup/
cat /sys/fs/cgroup/system.slice/monservice.service/memory.max

Réinitialiser les limites d'un service

systemctl set-property monservice.service --runtime

Sans argument, cela supprime les propriétés personnalisées du service.

Exemple complet : slice pour base de données

# /etc/systemd/system/db.slice [Unit] Description=Slice pour les services de base de données Before=slices.target
[Slice] CPUAccounting=true CPUWeight=1000 MemoryAccounting=true MemoryMax=8G MemoryHigh=6G IOAccounting=true IOWeight=800 TasksMax=500

Attribuez vos services PostgreSQL, MySQL ou MongoDB à ce slice pour leur réserver des ressources prioritaires.

Rendre les modifications permanentes

Méthode 1 : Fichier drop-in

sudo mkdir -p /etc/systemd/system/monservice.service.d/
sudo nano /etc/systemd/system/monservice.service.d/limits.conf
[Service] MemoryMax=1G CPUQuota=100%
sudo systemctl daemon-reload sudo systemctl restart monservice.service

Méthode 2 : Directement dans le fichier unit

Éditez le fichier dans /etc/systemd/system/ (jamais dans /lib/systemd/system/ car il serait écrasé lors des mises à jour).

Bonnes pratiques

  • Activez toujours CPUAccounting=true et MemoryAccounting=true sur le slice parent pour que les limites fonctionnent
  • Utilisez MemoryHigh (limite souple) plutôt que MemoryMax (limite stricte) pour éviter les kills OOM brusques
  • Groupez les services par fonctionnalité dans des slices dédiés (web, base de données, batch)
  • Surveillez avec systemd-cgtop pour ajuster les limites
  • Testez les limites avec des charges réalistes avant production
  • Documentez vos slices et les raisons des limites choisies

Dépannage

Le service est tué par OOM (Out of Memory)

Augmentez MemoryMax ou utilisez MemoryHigh pour un amortissement progressif. Vérifiez avec journalctl -xe.

Le service est limité en CPU

Augmentez CPUQuota ou réduisez le CPUWeight des autres services.

Les limites ne s'appliquent pas

Vérifiez que le service appartient bien au slice avec systemctl show monservice.service -p Slice.

Voir les logs d'un slice

journalctl -k -u system.slice

Les cgroups systemd offrent un contrôle puissant et granulaire sur les ressources système. En combinant slices, services et directives de limitation, vous pouvez isoler, prioriser et surveiller chaque charge de travail sur votre serveur Linux.
