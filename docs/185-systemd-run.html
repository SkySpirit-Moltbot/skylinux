185. systemd-run — Exécuter des commandes dans un contexte systemd isolé

Vous avez besoin de lancer une commande avec un timeout, un utilisateur spécifique, des limites de ressources, ou un environnement isolé, sans créer un service permanent ? systemd-run est l'outil parfait. Il crée un unité systemd transient (temporaire) pour exécuter n'importe quelle commande dans un contexte systemd contrôlé.

Pourquoi utiliser systemd-run ?

Quand vous exécutez une commande directement dans le shell, elle hérite de votre session, de vos variables, de vos droits. systemd-run permet de :

  • Isoler la commande dans son propre contexte systemd
  • Appliquer des limites de mémoire, CPU, nombre de fichiers ouverts
  • Définir une priorité nice différente
  • Changer d'utilisateur ou de groupe pour la commande
  • Définir un working directory précis
  • Obtenir des métriques précises (temps CPU, mémoire utilisée)
  • Créer un scope transient pour regrouper plusieurs processus

Syntaxe de base

systemd-run [OPTIONS] COMMAND [ARGUMENTS...]

Exemple le plus simple :

systemd-run echo "Bonjour depuis systemd"

La sortie indique le nom de l'unité créée :

Running as unit: run-r1234567890abc.service

Les deux modes : service vs scope

Par défaut : unité de type service (.service)

systemd-run crée une unité transient de type service. L'option --scope change ce comportement.

# Mode service (par défaut) systemd-run --unit=mon-service date # Mode scope systemd-run --scope sleep 30

Différence fondamentale

ModeType d'unitéUtilisation监控

Options de timeout et d'exécution

Définir un timeout maximal

Par défaut, systemd-run n'a pas de timeout. Utilisez --on-active, --on-boot, etc., ou --timer-timeout :

# La commande sera arrêtée après 30 secondes systemd-run --timer-timeout=30 sleep 60

Ou via l'option -r (remain_after_exit) pour un service qui reste actif :

# Avec un timeout de 30 secondes systemd-run --property=TimeoutStartSec=30 sleep 60

Exécuter après un délai

Planifier l'exécution dans le futur :

# Exécuter dans 5 minutes systemd-run --on-active="5min" echo "5 minutes plus tard"
# Exécuter au prochain démarrage systemd-run --on-boot echo "Au démarrage"
# Exécuter dans 1 heure systemd-run --on-active="+1h" rsync -a /home/ backup:/backups/

Exécuter à une heure précise

# Exécuter demain à 3h du matin systemd-run --on-calendar="*-*-* 03:00:00" /opt/backup.sh

Exécuter avec un autre utilisateur ou groupe

Changer d'utilisateur

# Exécuter en tant que l'utilisateur www-data systemd-run --uid=www-data whoami # Affiche : www-data

Changer d'utilisateur ET de groupe

# Exécuter en tant que l'utilisateur et groupe www-data systemd-run --uid=www-data --gid=www-data whoami

Spécifier plusieurs groupes supplémentaires

systemd-run --uid=www-data --set-group=www-data,adm id

Limiter les ressources

systemd-run peut appliquer des limites de ressources via les propriétés systemd :

Limite de mémoire

# Limiter à 512 Mo de mémoire systemd-run --property=MemoryMax=512M stress --vm 1 --vm-bytes 1G

Le processus sera tué si il dépasse 512 Mo.

Limite de temps CPU

# Limiter à 50% d'un cœur CPU systemd-run --property=CPUQuota=50% ./mon_script_cpu_intensif.sh

Limite sur le nombre de fichiers ouverts

systemd-run --property=LimitNOFILE=100 ./script_qui_ouvre_des_fichiers.sh

Combiner plusieurs limites

systemd-run \ --property=MemoryMax=1G \ --property=CPUQuota=200% \ --property=LimitNOFILE=4096 \ ./traitement_lourd.sh

Définir un répertoire de travail

# Exécuter depuis un répertoire spécifique systemd-run --working-directory=/var/log ls -la

Définir des variables d'environnement

# Avec une variable d'environnement systemd-run --set-env=MA_VARIABLE=valeur echo $MA_VARIABLE
# Avec plusieurs variables systemd-run \ --set-env=DB_HOST=localhost \ --set-env=DB_PORT=5432 \ ./script_database.sh

Définir la priorité nice

# Exécuter avec une priorité basse (pour les tâches de fond non critiques) systemd-run --nice=19 rsync -a /home/ backup:/backups/
# Exécuter avec une priorité haute (moins courant) systemd-run --nice=-10 ./tache_critique.sh

Nommer l'unité explicitement

# Donner un nom lisible à l'unité systemd-run --unit=sauvegarde-quotidienne /opt/backup.sh # Résultat : Running as unit: sauvegarde-quotidienne.service

Sans --unit, systemd génère un nom automatique comme run-r123abc456.service.

Visualiser les logs de l'unité

Une fois l'unité créée, ses logs sont accessibles via journalctl :

# Lancer avec génération de logs systemd-run --unit=mon-test date # Consulter les logs journalctl -u mon-test

Pour une exécution avec sortie capturée automatiquement :

# La sortie stdout/stderr est automatiquement journalisée systemd-run --unit=test-logs sh -c 'echo "Test"; ls /tmp' journalctl -u test-logs --no-pager

Scopes transient : regrouper plusieurs processus

Un scope permet de rattacher plusieurs processus à un même groupe de contrôle systemd :

# Créer un scope et y lancer un processus systemd-run --scope --unit=mon-groupe sleep 30 &
# Ajouter un autre processus au même scope (depuis un autre terminal) systemd-run --scope --unit=mon-groupe sleep 20 # Vérifier les processus du scope systemctl status mon-groupe.scope

Tous les processus du scope partagent les mêmes limites et peuvent être arrêtés d'un coup :

systemctl stop mon-groupe.scope # Arrête tous les processus du scope

Atelier pratique : backup isolé avec ressources limitées

Scénario

Vous voulez exécuter une sauvegarde rsync qui ne doit pas dépasser 1 Go de RAM et 50% CPU, tournant en tant qu'utilisateur backup, depuis le répertoire /backups.

systemd-run \ --unit=backup-quotidien \ --uid=backup \ --gid=backup \ --working-directory=/backups \ --property=MemoryMax=1G \ --property=CPUQuota=50% \ rsync -a /home/ /backups/home-$(date +%Y%m%d)/

Vérifier l'exécution

# Statut de l'unité systemctl status backup-quotidien.service # Logs journalctl -u backup-quotidien -f # Ressources utilisées systemctl show backup-quotidien.service | grep -E "Memory|CPU"

Atelier pratique : tâche périodique avec timer

Combiner systemd-run avec un timer transient pour une tâche qui s'exécute une fois :

# Créer un service transient systemd-run \ --unit=nettoyage-temp \ --on-active="+1h" \ --property=MemoryMax=256M \ find /tmp -type f -atime +7 -delete

Pour une exécution répétée, utilisez un timer permanent :

# Créer le service cat > /etc/systemd/system/nettoyage-tmp.service << 'EOF' [Unit] Description=Nettoyage fichiers temporaires [Service] Type=oneshot ExecStart=/usr/bin/find /tmp -type f -atime +7 -delete MemoryMax=256M EOF # Créer le timer cat > /etc/systemd/system/nettoyage-tmp.timer << 'EOF' [Unit] Description=Exécuter nettoyage-tmp.service chaque jour à 2h [Timer] OnCalendar=*-*-* 02:00:00 Persistent=true [Install] WantedBy=timers.target EOF # Activer et démarrer systemctl enable --now nettoyage-tmp.timer

Bonnes pratiques

  • Nommez vos unités avec --unit pour faciliter le suivi dans journalctl -u
  • Utilisez toujours des limites de ressources (MemoryMax, CPUQuota) pour les tâches non surveillées
  • Exécutez avec un utilisateur non-root (--uid) sauf si vraiment nécessaire
  • Combinez avec --set-env pour un environnement propre et reproductible
  • Consultez les logs avec journalctl -u NOM -xe après l'exécution
  • Pour les tâches récurrentes, préférez créer de vrais fichiers unit dans /etc/systemd/system/
  • systemd-run est idéal pour les scripts de maintenance,备份, ou tâches de conversion qui risqueraient de tourner indéfiniment
