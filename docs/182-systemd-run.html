182. systemd-run — Exécuter des commandes dans un contexte systemd isolé

La commande systemd-run permet d'exécuter n'importe quelle commande dans un contexte systemd temporaire, avec son propre scope, ses propres limites de ressources et son propre journal. C'est l'outil idéal pour isoler des processus sans créer de service permanent.

Pourquoi utiliser systemd-run ?

Quand vous lancez une commande normalement, elle hérite de l'environnement du shell parent. Avec systemd-run, vous créez un contexte isolé qui :

  • Possède son propre groupe de contrôle (cgroup)
  • Peut être limité en mémoire, CPU, ou nombre de processus
  • Génère des logs dans journald
  • Peut être tué proprement avec systemd-run --scope
  • Permet de définir un timer pour l'exécution retardée

Syntaxe de base

systemd-run [OPTIONS] COMMAND [ARGUMENTS...]

Exécution simple

L'exemple le plus basique — exécuter une commande dans un scope temporaire :

systemd-run --scope sleep 30

Cette commande crée un scope transient nommé scope-sleep.service et y exécute sleep 30. Vous pouvez vérifier son existence avec :

systemctl list-units --type=scope | grep sleep

Options principales

OptionDescription
--scopeCrée un scope transient (par défaut)
--unit=NOMNom personnalisé pour l'unité temporaire
--property=PROP=VALDéfinit une propriété systemd (MemoryMax, CPUWeight...)
-u, --unitSpécifie le nom de l'unité de service
-r, --remain-after-exitGarde l'unité active même après la fin du processus
--on-calendar=SPECPlanifie l'exécution (crée un timer transient)
-t, --ptyAlloue un pseudo-terminal (interaction possible)
-q, --quietSupprime les messages d'information
-E VAR=VALDéfinit une variable d'environnement
-p, --set-propertyAlias pour --property (plus court)

Exemples pratiques

1. Limiter la mémoire d'un processus

Imaginez un script qui consomme beaucoup de RAM. Vous pouvez le borner à 500 Mo :

systemd-run --scope -p MemoryMax=500M mon_gros_script.sh

Si le script dépasse 500 Mo de mémoire, il sera tué par OOM Killer de façon propre.

2. Exécuter avec un nom d'unité personnalisé

systemd-run --unit=backup_quotidienne /opt/scripts/backup.sh

L'unité sera visible dans systemctl list-units sous le nom backup_quotidienne.service.

3. Planifier une exécution différée avec timer

systemd-run --on-calendar="2026-10-23 08:00:00" /opt/scripts/maintenance.sh

Cela crée un timer transient qui lancera la commande à la date spécifiée.

Pour une exécution dans 5 minutes :

systemd-run --on-calendar="+5min" /opt/scripts/maintenance.sh

4. Exécuter en tant que service temporaire (--unit vs --scope)

--scope crée un scope qui englobe le processus. --unit seul crée un service transient :

systemd-run --unit=mon_service date

Le service apparaît dans systemctl list-units --type=service au lieu de --type=scope.

5. Combiner avec des propriétés CPU

systemd-run -p CPUWeight=200 tar -czf backup.tar.gz /home

Le processus aura une priorité CPU plus élevée (200 au lieu de 100 par défaut).

6. Définir des variables d'environnement

systemd-run -E MAILTO="admin@example.com" /opt/scripts/rapport.sh

7. Mode interactif avec PTY

systemd-run -t --scope bash

Ouvre un shell interactif dans un scope systemd. Pratique pour tester l'environnement.

Visualiser les logs des unités transient

Tous les output stdout/stderr sont capturés par journald. Consultez-les avec :

journalctl -u backup_quotidienne.service

Ou pour le dernier scope créé :

journalctl --user-unit=scope-sleep

Comparaison avec les alternatives

MéthodeAvantageInconvénient
nohupSimple, survie aux déconnexionsPas de limites de ressources, pas de journal
screen/tmuxSession persistante interactivePas d'isolation ni de limites
cronPlanification récurrentePas de limites, exécution différée unique complexe
systemd-runIsolation, limites, journalisation, timersNécessite systemd (quasi-universel)

Cas d'utilisation réels

Scripts de backup avec limites mémoire

systemd-run --scope \ -p MemoryMax=1G \ -p IOSchedulingClass=idle \ /opt/scripts/backup_incremental.sh

Test de consommation mémoire d'un programme

systemd-run --unit=test_mem -p MemoryMax=100M -- bash -c 'while true; do :; done'

Ensuite, vérifiez :

systemctl status test_mem systemd-cgtop

Exécution retardée simple

systemd-run --on-calendar="+1hour" /opt/scripts/nettoyer_cache.sh

Bonnes pratiques

  • Utilisez toujours --scope ou --unit pour identifier vos executions transient
  • Définissez des limites de mémoire réalistes pour éviter les surprises
  • Conservez les logs avec journalctl -u NOM pour le débogage
  • Pour des tâches récurrentes, préférez un vrai fichier unit dans /etc/systemd/system/
  • Combinez avec -p IOSchedulingClass=idle pour les tâches volumineuses non critiques

Résumé

systemd-run est l'outil idéal pour :

  • Isoler des processus sans service permanent
  • Appliquer des limites de ressources
  • Journaliser l'output de commandes
  • Planifier des exécutions uniques avec des timers
  • Créer des environnements de test isolés
