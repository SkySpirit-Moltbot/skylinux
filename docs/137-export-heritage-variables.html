export — Héritage et propagation des variables dans les scripts

Quand vous lancez un script ou une commande dans le terminal, un nouvel environnement est créé. Toutes les variables ne sont pas automatiquement visibles de l'intérieur. La commande export est la clé qui contrôle cette propagation. Comprendre son fonctionnement est essentiel pour écrire des scripts robustes et comprendre pourquoi certaines variables "disparaissent" entre les appels.

La différence entre variable et variable exportée

Une variable simple n'existe que dans le shell courant. Elle n'est pas transmise aux processus enfants (les commandes ou scripts que vous lancez).

MA_VARIABLE="Bonjour"

Vérifions ce que voit une commande enfant :

echo "$MA_VARIABLE"
# Résultat : vide — la variable n'est pas visible ici

Maintenant, rendons-la exportable :

export MA_VARIABLE="Bonjour"
echo "$MA_VARIABLE"
# Résultat : Bonjour

Les trois façons de déclarer une variable exportée

1. export avec déclaration

export NOM="David"

La variable est créée et marquée pour l'export en une seule commande.

2. export sur une variable existante

AGE=25 export AGE

On crée d'abord la variable, puis on l'exporte séparément. Équivalent à export AGE=25.

3. readonly + export

export CHEMIN="/opt/outils" readonly CHEMIN

Une variable peut être à la fois exportée et en lecture seule. Une fois figée, elle ne peut plus être modifiée ni désexportée.

Visualiser l'environnement exporté

Liste de toutes les variables exportées

export -p

Cette commande affiche toutes les variables exportées dans le shell courant, avec la syntaxe export complète. Utile pour débugger.

Liste simplifiée

env

Affiche l'intégralité de l'environnement : chaque ligne est CLE=VALEUR.

Une variable précise

echo "$PATH"

PATH est la variable la plus célèbre : elle contient la liste des répertoires où le shell cherche les commandes.

Comprendre l'héritage parent → enfant

Le principe fondamental

Quand vous lancez un script ou une commande, un processus enfant est créé. Ce processus reçoit une copie de l'environnement du parent. Le parent et l'enfant ne partagent pas la mémoire : les modifications de l'enfant n'affectent jamais le parent.

#!/bin/bash # script_enfant.sh echo "L'enfant voit : $MA_VAR"
MA_VAR="Valeur secrète" ./script_enfant.sh # L'enfant ne la voit PAS
export MA_VAR="Valeur secrète" ./script_enfant.sh # L'enfant la voit

L'inverse ne marche jamais

#!/bin/bash # script_enfant.sh MA_VAR="Modifiée par l'enfant"
./script_enfant.sh echo "$MA_VAR" # Affiche : Modifiée par l'enfant

Cela fonctionne car le script s'exécute dans le même shell si vous le "sourced" (avec source ou .), pas dans un sous-shell.

export vs source : deux modes d'exécution

Exécution dans un sous-shell (par défaut)

./mon_script.sh bash mon_script.sh

Le script s'exécute dans un processus enfant. Seules les variables export lui sont transmises.

Exécution dans le shell courant (source)

source ./mon_script.sh . ./mon_script.sh

Le script s'exécute dans le shell courant. Toutes les variables définies dans le script existent dans votre terminal après l'exécution. Aucun export n'est nécessaire pour "remonter" les valeurs.

Cela explique pourquoi ~/.bashrc ou ~/.profile utilisent export : ces fichiers sont sourcés au démarrage du shell, pas exécutés dans un sous-shell.

La variable d'environnement speciale : ENV

Quand un shell interactif démarre, il lit automatiquement le fichier pointé par $ENV :

echo "$ENV"

Généralement, c'est ~/.bashrc. Vous pouvez personnaliser ce comportement :

export ENV="$HOME/.bash_perso"

Tout ce que vous ajoutez dans ce fichier sera exécuté à chaque nouveau shell interactif.

Supprimer une variable exportée

Pour retirer une variable de l'environnement exporté (sans supprimer la variable elle-même) :

export -n MA_VARIABLE

Après cela, MA_VARIABLE existe toujours dans le shell, mais n'est plus transmise aux processus enfants.

Pour supprimer complètement une variable :

unset MA_VARIABLE

unset supprime la variable de tous les contextes (shell + export). Exception : les variables readonly ne peuvent pas être unsetées.

Transmission selective : env -i

Parfois, vous voulez lancer une commande avec un environnement vide (propre), sans les variables du shell courant :

env -i /home/user/mon_script.sh

env -i efface tout l'environnement avant d'exécuter la commande. Seules les variables que vous ajoutez explicitement seront présentes.

Combiner -i et export

env -i HOME=/home/user PATH=/usr/bin:/bin ./script_propre.sh

Ce mode est utile pour tester qu'un script fonctionne avec un environnement minimal et prévisible.

Debogage : suivre ce qui est transmis

Voir l'environnement d'un script

#!/bin/bash echo "=== ENVIRONNEMENT REÇU ===" env | sort echo "=== FIN ==="

Traces avec bash -x

bash -x ./mon_script.sh

Active le mode trace : chaque commande est affichée avec le préfixe + avant son exécution. Permet de suivre précisément le cheminement du script.

Exporter une trace

BASH_XTRACEFD=3 exec 3>/tmp/trace.log set -x source ./mon_script.sh 2>&3

Cette technique avancée redirige les traces vers un fichier dédié sans polluer la sortie standard.

Cas d'utilisation courants

1. Configurer un projet

# config.sh export PROJET_ROOT="/home/user/monprojet" export PROJET_ENV="production" export LOG_LEVEL="debug"
source ./config.sh ./build.sh # build.sh voit les variables exportées ./deploy.sh # deploy.sh aussi

2. CI/CD et scripts automatises

export API_KEY="secret123" export DEPLOY_TARGET="production" ./deploy.sh

Les variables exportées dans le shell parent sont disponibles pour tous les scripts appelés ensuite.

3. Environment wrapper

#!/bin/bash # env_python.sh export PYTHONPATH="/opt/projet/lib:$PYTHONPATH" export DJANGO_SETTINGS_MODULE="projet.settings.prod" exec "$@"
chmod +x env_python.sh ./env_python.sh python manage.py runserver

Ce wrapper prépare l'environnement puis exécute la commande passée en argument avec les variables définies.

La commande export est un pilier de l'écriture de scripts Linux. Elle contrôle la frontière invisible entre le shell parent et ses enfants, et comprendre cette frontière évite bien des surprises quand une variable "disparaît" mystérieusement.
